# Implementation checkpoint: reference and accounting core

17 September 2026. Implements the first delivery slice of
[the replacement specification](controller-plan-execution.md).

**This checkpoint is not the live-controller cutover.** The new producer and
consumer run together in contract tests. Production request handlers, the native
command host and the existing battery card have not yet been switched to them.
No device mode, release channel or production rollout order changes here.

## Implemented

- Backend `battery-plan-execution.ts` materialises a versioned battery contract
  from the final planner schedule and its exact flow rows. It publishes explicit
  partial intervals, integer mWh, storage bounds, nominal roles, source/export
  permissions, the distinct export reserve, typed objectives and dispositions.
- Recovery is delegated inside an existing selected charging window, with
  nominal demand allocated first and deterministic earliest recovery. It does
  not authorise purchases in a different economic window. A planner can supply
  additional justified windows later through the same contract.
- Integration `plan_execution.py` validates the contract, records immutable
  reference admissions and receipt-ordered meter evidence, derives gross-flow
  bounds, debt/credit and separate state residuals, and versions objective
  amendments. Stable event identities make corrections and retries distinct.
- Replan generation and the incorporated receipt prefix are explicit. Handover
  records the common-instant reference adjustment without inventing delivered
  energy or adding incorporated debt to a new target twice. Historical misses
  remain separate from transfer or retirement of responsibility.
  `capture_replan` captures the generation and complete feedback payload in one
  pure transition; later receipts cannot change a request already in flight.
- The pure assessment follows the nominal role and authorised correction. It
  applies measured demand, empirical conversion, real import headroom, pending
  load effects, supply attribution, storage bounds and export reserve. It has no
  price ranking, future optimiser or discretionary switching timer.
- The existing empirical loss-collection/fitting code is retained and used by
  assessment. The nominal reference declares its planner conversion assumptions;
  actual DC counter increments are not multiplied by nominal efficiency again.
- A plain-language card read model describes plan, measured behaviour, difference
  and next action. It distinguishes Verification and requested charging from
  measured delivery. The frontend wiring and layout are unchanged in this slice.

The new shared fixture is generated by
`scripts/generate-battery-execution-fixture.ts` in the backend from the real planner,
including a seven-minute first interval. The Python consumer reads the generated
contract without field translation. The generator's output is copied to
`tests/fixtures/battery-plan-execution-v1.json` in this integration; compare the two
files when regenerating. Neither fixture is hand-authored.

## Review corrections included

The independent read-only review found cases now covered by regression traces:
stop charging at an achieved target; subtract spent recovery allowance from
remaining feasibility; retain versions of an amended target; prevent replay from
undoing a correction; request replanning for an observed state shortfall without
inventing flow debt; preserve the separate export reserve. Other traces cover
partial/unknown meter intervals, nonzero opening debt/credit, late correction
after handover, missed deadlines, immutable deadlines, duplicate plans, local
request supersession, current supply scope and unchanged-counter measured zero.

## Remaining before live replacement

1. Connect feedback capture and contract materialisation to the real snapshot,
   planning, ingestion and acknowledgement paths. Carry the request generation,
   actuals prefix, observed state and outstanding outcomes end to end. Bind the
   correct physical or battery-only Verification branch; this standalone producer
   is deliberately not inferred from an arbitrary top-level scenario.
2. Replace `home_runtime`'s policy session, ranking, timers and dispatch gate with
   the new execution/account session. Keep one atomic transition owner. Connect
   meter event identity and correction provenance to actual HA reports. Define
   bounded journal retention/indexing that preserves unresolved intervals,
   corrections and open objective history; the current pure account retains its
   evidence in full for deterministic traces.
3. Migrate existing physical command journals once: retain pending/ambiguous
   effects, writer identity and release authority while retiring economic
   selection. Connect account persistence, compatible restart, coalesced replans
   and native wakeups. Changed storage/capacity bases require explicit
   reconciliation; the current account fails admission instead of guessing it.
4. Remove the superseded live policy exchange/continuation decision path for the
   migrated battery scope. Connect the card read model and exportable accounting
   evidence in the existing layout. Do not keep dual decision owners or an old
   economic fallback.
5. Exercise the complete fake-service path, crash/transport and configuration
   correction traces, then commission the adapter through the existing rollout:
   **home battery first, pool heater next, EV afterwards**. Later device migration
   needs its own service fulfilment evidence; electrical kWh does not stand in
   for pool temperature or EV departure readiness.

This boundary provides a reviewable checkpoint before changing live command
ownership and persistent runtime state. It does not claim the replacement is
installed, production-ready, or proven on equipment.
